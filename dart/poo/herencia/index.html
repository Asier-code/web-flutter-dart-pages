    Herencia en Dart¶

    📄 Nota: Esta página forma parte de la guía completa Dart & Flutter. Todo el contenido proviene de ficheros de texto Markdown, lo que nos permite mantener la documentación versionada, colaborativa y fácil de actualizar con Git.

    Hay un momento en el desarrollo de cualquier aplicación en el que te das cuenta de que estás repitiendo código entre clases. Tienes una clase Empleado, luego una clase Manager, luego una clase Director... y todas tienen nombre, email y un método mostrarInfo. Las copias y pegas, y cuando tienes que cambiar algo, lo cambias en tres sitios. Eso es exactamente el problema que resuelve la herencia.

    ¿Qué es la herencia?¶

    La herencia es un mecanismo que permite que una clase tome prestado todo el comportamiento y las propiedades de otra clase, y encima añada o modifique lo que necesite. La clase de la que se hereda se llama superclase (o clase base o clase padre), y la que hereda se llama subclase (o clase derivada o clase hija).

    La relación que describe la herencia es siempre de tipo "es un":

    • Un Perro es un Animal
    • Un Manager es un Empleado
    • Un Coche es un Vehiculo

    Si esa frase no tiene sentido con tus clases, probablemente la herencia no es lo que necesitas (y al final de esta página veremos alternativas).

    En Dart, la herencia se declara con la palabra clave extends:

    class SubClase extends SuperClase {
  // todo lo de SuperClase ya está aquí disponible
}

    Una cosa importante: Dart solo permite herencia simple. Una subclase solo puede extender una superclase. Si necesitas combinar comportamiento de varias fuentes, para eso están los mixins (que tienen su propia página en esta guía).

    Herencia básica — Empezando por un ejemplo real¶

    Vamos a construir un sistema sencillo de vehículos. Todos los vehículos comparten cosas: tienen una marca, un modelo, una velocidad actual y pueden acelerar o frenar. Lo que cambia es el tipo de vehículo y sus comportamientos específicos.

    // ─── SUPERCLASE ───────────────────────────────────────────
class Vehiculo {
  String marca;
  String modelo;
  int velocidadActual;
  int velocidadMaxima;

  Vehiculo({
    required this.marca,
    required this.modelo,
    required this.velocidadMaxima,
    this.velocidadActual = 0,
  });

  void acelerar(int kmh) {
    velocidadActual = (velocidadActual + kmh).clamp(0, velocidadMaxima);
    print('🚗 $marca $modelo acelera → $velocidadActual km/h');
  }

  void frenar(int kmh) {
    velocidadActual = (velocidadActual - kmh).clamp(0, velocidadMaxima);
    print('🛑 $marca $modelo frena → $velocidadActual km/h');
  }

  void mostrarEstado() {
    print('$marca $modelo | Velocidad: $velocidadActual/$velocidadMaxima km/h');
  }
}

// ─── SUBCLASES ────────────────────────────────────────────
class Coche extends Vehiculo {
  int numeroPuertas;

  // Usamos `super` para pasar los valores al constructor de Vehiculo
  Coche({
    required super.marca,
    required super.modelo,
    required super.velocidadMaxima,
    this.numeroPuertas = 4,
  });

  void abrirMaletero() {
    print('🔓 Maletero de $marca $modelo abierto.');
  }
}

class Moto extends Vehiculo {
  bool tieneSidecar;

  Moto({
    required super.marca,
    required super.modelo,
    required super.velocidadMaxima,
    this.tieneSidecar = false,
  });

  void hacerCaballito() {
    if (velocidadActual > 0) {
      print('🏍️  ¡$marca $modelo hace un caballito!');
    } else {
      print('⚠️  Necesitas moverte para hacer un caballito.');
    }
  }
}

// ─── MAIN ─────────────────────────────────────────────────
void main() {
  Coche coche = Coche(
    marca: 'Seat',
    modelo: 'León',
    velocidadMaxima: 220,
    numeroPuertas: 5,
  );

  Moto moto = Moto(
    marca: 'Honda',
    modelo: 'CB500',
    velocidadMaxima: 180,
  );

  print('── Coche ──────────────────────');
  coche.mostrarEstado();   // Heredado de Vehiculo
  coche.acelerar(80);      // Heredado de Vehiculo
  coche.acelerar(60);      // Heredado de Vehiculo
  coche.abrirMaletero();   // Propio de Coche
  coche.frenar(30);        // Heredado de Vehiculo

  print('\n── Moto ───────────────────────');
  moto.mostrarEstado();    // Heredado de Vehiculo
  moto.acelerar(50);       // Heredado de Vehiculo
  moto.hacerCaballito();   // Propio de Moto
  moto.hacerCaballito();   // Velocidad > 0, lo hace
}

    Observa cómo Coche y Moto no declaran marca, modelo ni los métodos acelerar o frenar, pero los usan perfectamente. Todo eso viene de Vehiculo. Cada subclase solo añade lo que la diferencia de las demás.

    La palabra clave super¶

    super es la referencia a la superclase desde dentro de la subclase. Tiene dos usos principales:

    Llamar al constructor de la superclase¶

    Cuando creas un objeto de una subclase, Dart necesita inicializar también la parte heredada. Para eso se llama al constructor de la superclase:

    // Sintaxis moderna (Dart 2.17+): super-parámetros
Coche({required super.marca, required super.modelo ...});

// Sintaxis clásica equivalente con lista de inicializadores
Coche({required String marca, required String modelo})
    : super(marca: marca, modelo: modelo);

    Ambas hacen lo mismo. La primera es más concisa y es la que verás en código Dart moderno.

    Llamar a métodos de la superclase¶

    Cuando sobreescribes un método en una subclase pero aún quieres ejecutar la lógica original, llamas a super.metodo():

    @override
void mostrarEstado() {
  super.mostrarEstado();           // Ejecuta el de Vehiculo primero
  print('Puertas: $numeroPuertas'); // Y luego añade lo propio
}

    Sobreescritura de métodos — @override¶

    Una subclase puede redefinir cualquier método de la superclase para cambiar su comportamiento. Esto es lo que hace la herencia realmente potente.

    En Dart se usa la anotación @override para dejar claro que estás sobreescribiendo intencionadamente un método heredado. No es obligatoria, pero el analizador te avisará si el método no existe en la superclase, lo que evita errores silenciosos.

    Veamos un ejemplo más completo con un sistema de notificaciones:

    // ─── SUPERCLASE ───────────────────────────────────────────
abstract class Notificacion {
  final String titulo;
  final String mensaje;
  final DateTime timestamp;

  Notificacion({
    required this.titulo,
    required this.mensaje,
    DateTime? timestamp,
  }) : timestamp = timestamp ?? DateTime.now();

  // Método base: comportamiento por defecto
  void enviar() {
    print('📤 Enviando notificación: "$titulo"');
  }

  // Método que describe el tipo (cada subclase lo sobreescribe)
  String describir() => 'Notificación genérica: $titulo';

  @override
  String toString() => '[$runtimeType] $titulo — ${timestamp.hour}:${timestamp.minute.toString().padLeft(2, "0")}';
}

// ─── SUBCLASES ────────────────────────────────────────────
class NotificacionEmail extends Notificacion {
  final String destinatario;

  NotificacionEmail({
    required super.titulo,
    required super.mensaje,
    required this.destinatario,
  });

  @override
  void enviar() {
    super.enviar(); // Reutilizamos el log de la superclase
    print('  📧 Email enviado a: $destinatario');
    print('  Asunto: $titulo');
    print('  Cuerpo: $mensaje');
  }

  @override
  String describir() => 'Email para $destinatario: $titulo';
}

class NotificacionPush extends Notificacion {
  final String dispositivoId;
  final bool urgente;

  NotificacionPush({
    required super.titulo,
    required super.mensaje,
    required this.dispositivoId,
    this.urgente = false,
  });

  @override
  void enviar() {
    super.enviar();
    String icono = urgente ? '🚨' : '🔔';
    print('  $icono Push enviada al dispositivo: $dispositivoId');
    if (urgente) print('  ⚡ MARCADA COMO URGENTE');
  }

  @override
  String describir() => '${urgente ? "[URGENTE] " : ""}Push → $dispositivoId: $titulo';
}

class NotificacionSMS extends Notificacion {
  final String telefono;

  NotificacionSMS({
    required super.titulo,
    required super.mensaje,
    required this.telefono,
  });

  @override
  void enviar() {
    super.enviar();
    // El SMS tiene límite de caracteres, así que truncamos
    String mensajeCorto = mensaje.length > 60
        ? '${mensaje.substring(0, 57)}...'
        : mensaje;
    print('  💬 SMS enviado a $telefono: "$mensajeCorto"');
  }

  @override
  String describir() => 'SMS a $telefono: $titulo';
}

// ─── MAIN ─────────────────────────────────────────────────
void main() {
  // Todas son Notificacion, pero cada una se comporta distinto
  List<Notificacion> cola = [
    NotificacionEmail(
      titulo: 'Bienvenida',
      mensaje: 'Gracias por registrarte en nuestra plataforma.',
      destinatario: 'ana@ejemplo.com',
    ),
    NotificacionPush(
      titulo: 'Nueva oferta',
      mensaje: '30% de descuento solo hoy.',
      dispositivoId: 'device-abc-123',
      urgente: true,
    ),
    NotificacionSMS(
      titulo: 'Código de verificación',
      mensaje: 'Tu código es 847291. Válido durante 5 minutos. No lo compartas con nadie.',
      telefono: '+34 612 345 678',
    ),
  ];

  print('═══════════════════════════════════');
  print('  COLA DE NOTIFICACIONES PENDIENTES');
  print('═══════════════════════════════════\n');

  for (int i = 0; i < cola.length; i++) {
    print('── Notificación ${i + 1} ──────────────');
    print('   ${cola[i].describir()}');
    cola[i].enviar();
    print('');
  }

  print('\n📋 Resumen:');
  cola.forEach((n) => print('  • $n'));
}

    Este ejemplo muestra algo muy importante: en el bucle for, tratamos todas las notificaciones como Notificacion (el tipo de la superclase), pero cada una ejecuta su propia versión de enviar() y describir(). Eso es polimorfismo, y es la consecuencia natural de combinar herencia con sobreescritura de métodos.

    Clases abstractas¶

    Cuando defines una superclase que nunca vas a instanciar directamente, porque existe solo para ser heredada, puedes marcarla como abstract. Una clase abstracta puede tener métodos sin implementación (métodos abstractos) que obligan a las subclases a definirlos.

    abstract class Forma {
  String color;

  Forma(this.color);

  // Método abstracto: sin cuerpo, las subclases DEBEN implementarlo
  double calcularArea();
  double calcularPerimetro();

  // Método concreto: tiene implementación, las subclases pueden heredarlo
  void describir() {
    print('Forma $color | Área: ${calcularArea().toStringAsFixed(2)} | Perímetro: ${calcularPerimetro().toStringAsFixed(2)}');
  }
}

class Circulo extends Forma {
  double radio;

  Circulo({required this.radio, required super.color});

  @override
  double calcularArea() => 3.14159 * radio * radio;

  @override
  double calcularPerimetro() => 2 * 3.14159 * radio;
}

class Rectangulo extends Forma {
  double ancho;
  double alto;

  Rectangulo({required this.ancho, required this.alto, required super.color});

  @override
  double calcularArea() => ancho * alto;

  @override
  double calcularPerimetro() => 2 * (ancho + alto);
}

void main() {
  List<Forma> formas = [
    Circulo(radio: 5.0, color: 'rojo'),
    Rectangulo(ancho: 8.0, alto: 3.5, color: 'azul'),
    Circulo(radio: 2.5, color: 'verde'),
  ];

  formas.forEach((f) => f.describir());

  // Forma con mayor área
  Forma mayor = formas.reduce((a, b) => a.calcularArea() > b.calcularArea() ? a : b);
  print('\nForma más grande: ${mayor.color} con área ${mayor.calcularArea().toStringAsFixed(2)}');

  // Intentar instanciar una clase abstracta daría error de compilación:
  // var f = Forma('negro'); // ❌ Error: Abstract classes can't be instantiated
}

    💡 Tip: Las clases abstractas son ideales cuando tienes un concepto genérico que nunca existe "solo" en tu dominio. Una Forma pura no existe; existen círculos, rectángulos, triángulos. Un Animal puro tampoco; existen perros, gatos, águilas.

    Comprobar el tipo con is e is!¶

    Cuando trabajas con herencia y listas de superclases, a veces necesitas saber de qué tipo real es un objeto. Para eso están los operadores is e is!:

    void main() {
  Notificacion n = NotificacionPush(
    titulo: 'Prueba',
    mensaje: 'Hola',
    dispositivoId: 'device-001',
  );

  print(n is Notificacion);      // true  — es una Notificacion
  print(n is NotificacionPush);  // true  — es específicamente una Push
  print(n is NotificacionEmail); // false — no es un Email

  // Casting seguro con `as` tras verificar con `is`
  if (n is NotificacionPush) {
    // Dentro del if, Dart ya sabe que `n` es NotificacionPush
    print('Dispositivo: ${n.dispositivoId}');
  }
}

    Consejos y buenas prácticas¶

    1. Úsala solo cuando la relación "es un" tiene sentido de verdad¶

    La herencia es potente, pero se abusa de ella. Antes de escribir extends, pregúntate: ¿una instancia de la subclase es realmente una instancia de la superclase en todos los contextos? Si la respuesta es "más o menos" o "en algunos casos", mejor usar composición o mixins.

    // ❌ ¿Un Logger "es un" Servicio? No realmente.
class Logger extends Servicio { ... }

// ✅ El servicio "tiene un" Logger (composición)
class Servicio {
  final Logger _logger = Logger();
}

    2. Mantén las jerarquías poco profundas¶

    Una cadena de herencia de 4 o 5 niveles es muy difícil de seguir. Si llegas a ese punto, es señal de que la estructura necesita replantearse. En general, dos niveles (Base → Especialización) suele ser suficiente.

    3. Usa @override siempre al sobreescribir¶

    No es obligatorio, pero sí necesario. Sin @override, si cambias el nombre del método en la superclase, la subclase tendrá silenciosamente un método nuevo en lugar del sobreescrito.

    // ✅ El analizador te avisa si `enviar` no existe en la superclase
@override
void enviar() { ... }

    4. Llama a super cuando el método padre hace algo útil¶

    Si sobreescribes un método que ya tiene lógica en la superclase y esa lógica sigue siendo válida, llama a super.metodo() en lugar de duplicar el código.

    @override
void enviar() {
  super.enviar(); // ✅ Reutiliza el log, registro o validación del padre
  // ... lógica específica de la subclase
}

    5. Prefiere clases abstractas para superclases que nunca se instancian solas¶

    Si tu superclase existe solo como molde para las subclases, márcala como abstract. Así queda claro que no tiene sentido instanciarla directamente y el compilador te ayuda a garantizarlo.

    6. Documenta la jerarquía en proyectos grandes¶

    En proyectos con muchas clases, un comentario o un diagrama de herencia en el index.md de la sección vale oro para el desarrollador que se incorpora al equipo.
