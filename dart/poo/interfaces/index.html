    Interfaces en Dart¶

    📄 Nota: Esta página forma parte de la guía completa Dart & Flutter. Todo el contenido proviene de ficheros de texto Markdown, lo que nos permite mantener la documentación versionada, colaborativa y fácil de actualizar con Git.

    Imagina que estás construyendo una app de pagos. Tienes que integrar PayPal, Stripe y una pasarela bancaria propia. Las tres funcionan de forma completamente diferente por dentro, pero desde el punto de vista de tu app, todas deben poder hacer lo mismo: procesar un pago, emitir un reembolso y comprobar el estado de una transacción.

    Lo que necesitas es un contrato: un acuerdo que diga "cualquier cosa que quiera actuar como pasarela de pago debe tener estos métodos". Eso es exactamente lo que hace una interfaz.

    ¿Qué es una interfaz en Dart?¶

    Una interfaz define un contrato de comportamiento: una lista de métodos y propiedades que una clase se compromete a implementar. No contiene lógica, solo la firma de lo que debe existir.

    Dart tiene algo curioso que lo diferencia de Java o Kotlin: no existe una palabra clave interface. En su lugar, cualquier clase puede actuar como interfaz. Cuando usas implements con una clase, te comprometes a implementar todos sus miembros desde cero, ignorando cualquier implementación que ya tuviera.

    // En Dart, esto actúa como una interfaz
abstract class PasarelaDePago {
  Future<bool> procesarPago(double cantidad);
  Future<bool> emitirReembolso(String transaccionId);
  String get nombre;
}

// Esta clase "firma el contrato"
class PayPalGateway implements PasarelaDePago {
  @override
  Future<bool> procesarPago(double cantidad) async { ... }

  @override
  Future<bool> emitirReembolso(String transaccionId) async { ... }

  @override
  String get nombre => 'PayPal';
}

    Si PayPalGateway no implementa alguno de esos miembros, el compilador lanza un error. El contrato es obligatorio, no opcional.

    Interfaces con clases abstractas¶

    La forma más habitual y recomendada de definir una interfaz en Dart es usando una clase abstracta. Así queda claro que esa clase existe solo para ser implementada, no para ser instanciada directamente.

    abstract class Autenticable {
  // El contrato: toda clase que implemente esto debe tener estos métodos
  Future<bool> iniciarSesion(String email, String password);
  Future<void> cerrarSesion();
  bool get estaAutenticado;
}

// Implementación para autenticación con email y contraseña
class AuthEmail implements Autenticable {
  bool _autenticado = false;
  String? _emailActual;

  @override
  Future<bool> iniciarSesion(String email, String password) async {
    await Future.delayed(Duration(milliseconds: 500)); // simula llamada a API
    // Lógica simplificada para el ejemplo
    if (password.length >= 6) {
      _autenticado = true;
      _emailActual = email;
      print('✅ [$runtimeType] Sesión iniciada para $email');
      return true;
    }
    print('❌ [$runtimeType] Contraseña incorrecta o muy corta.');
    return false;
  }

  @override
  Future<void> cerrarSesion() async {
    _autenticado = false;
    print('👋 [$runtimeType] Sesión cerrada para $_emailActual');
    _emailActual = null;
  }

  @override
  bool get estaAutenticado => _autenticado;
}

// Implementación para autenticación con Google
class AuthGoogle implements Autenticable {
  bool _autenticado = false;

  @override
  Future<bool> iniciarSesion(String email, String password) async {
    await Future.delayed(Duration(milliseconds: 300));
    // En una app real, esto abriría el flujo OAuth de Google
    _autenticado = true;
    print('✅ [$runtimeType] Autenticado con Google: $email');
    return true;
  }

  @override
  Future<void> cerrarSesion() async {
    _autenticado = false;
    print('👋 [$runtimeType] Sesión de Google cerrada.');
  }

  @override
  bool get estaAutenticado => _autenticado;
}

// Función que trabaja con el contrato, no con implementaciones concretas
Future<void> flujoDeAcceso(Autenticable auth, String email, String pass) async {
  print('\n── Iniciando flujo con ${auth.runtimeType} ──────');
  print('¿Autenticado antes? ${auth.estaAutenticado}');
  bool exito = await auth.iniciarSesion(email, pass);
  if (exito) {
    print('¿Autenticado ahora? ${auth.estaAutenticado}');
    await auth.cerrarSesion();
  }
}

void main() async {
  await flujoDeAcceso(AuthEmail(),  'ana@ejemplo.com', 'mipassword');
  await flujoDeAcceso(AuthGoogle(), 'ana@gmail.com',   '');
}

    Hay algo importante en flujoDeAcceso: recibe un Autenticable, no un AuthEmail ni un AuthGoogle. No le importa la implementación concreta, solo que el objeto cumple el contrato. Esto es exactamente la potencia de las interfaces: el código que las consume es independiente de cómo se implementan.

    Implementar múltiples interfaces¶

    Una de las ventajas de implements frente a extends es que una clase puede implementar tantas interfaces como necesite. Esto permite construir clases muy expresivas que cumplen varios contratos a la vez.

    // ─── INTERFACES ───────────────────────────────────────────
abstract class Exportable {
  String exportarCSV();
  String exportarJSON();
}

abstract class Filtrable {
  List<dynamic> filtrarPor(String campo, dynamic valor);
  List<dynamic> ordenarPor(String campo, {bool descendente = false});
}

abstract class Paginable {
  List<dynamic> paginar({required int pagina, required int porPagina});
  int get totalPaginas;
  int get totalElementos;
}

// ─── MODELO ───────────────────────────────────────────────
class Producto {
  final String id;
  final String nombre;
  final String categoria;
  final double precio;
  final int stock;

  const Producto({
    required this.id,
    required this.nombre,
    required this.categoria,
    required this.precio,
    required this.stock,
  });

  @override
  String toString() => '$nombre (${precio.toStringAsFixed(2)} €)';
}

// ─── REPOSITORIO QUE IMPLEMENTA LOS TRES CONTRATOS ────────
class RepositorioProductos implements Exportable, Filtrable, Paginable {
  final List<Producto> _datos;

  RepositorioProductos(this._datos);

  // ── Exportable ──────────────────────────────────────────
  @override
  String exportarCSV() {
    final cabecera = 'id,nombre,categoria,precio,stock';
    final filas = _datos.map((p) =>
      '${p.id},${p.nombre},${p.categoria},${p.precio},${p.stock}'
    );
    return '$cabecera\n${filas.join("\n")}';
  }

  @override
  String exportarJSON() {
    final items = _datos.map((p) =>
      '{"id":"${p.id}","nombre":"${p.nombre}","precio":${p.precio},"stock":${p.stock}}'
    );
    return '[${items.join(",")}]';
  }

  // ── Filtrable ───────────────────────────────────────────
  @override
  List<Producto> filtrarPor(String campo, dynamic valor) {
    return _datos.where((p) {
      switch (campo) {
        case 'categoria': return p.categoria == valor;
        case 'disponible': return valor == true ? p.stock > 0 : p.stock == 0;
        default: return false;
      }
    }).toList();
  }

  @override
  List<Producto> ordenarPor(String campo, {bool descendente = false}) {
    final copia = List<Producto>.from(_datos);
    copia.sort((a, b) {
      int cmp;
      switch (campo) {
        case 'precio': cmp = a.precio.compareTo(b.precio); break;
        case 'nombre': cmp = a.nombre.compareTo(b.nombre); break;
        case 'stock':  cmp = a.stock.compareTo(b.stock);   break;
        default: cmp = 0;
      }
      return descendente ? -cmp : cmp;
    });
    return copia;
  }

  // ── Paginable ───────────────────────────────────────────
  @override
  int get totalElementos => _datos.length;

  @override
  int totalPaginasPara(int porPagina) => (_datos.length / porPagina).ceil();

  @override
  int get totalPaginas => totalPaginasPara(5); // Valor por defecto

  @override
  List<Producto> paginar({required int pagina, required int porPagina}) {
    final inicio = (pagina - 1) * porPagina;
    if (inicio >= _datos.length) return [];
    final fin = (inicio + porPagina).clamp(0, _datos.length);
    return _datos.sublist(inicio, fin);
  }
}

// ─── MAIN ─────────────────────────────────────────────────
void main() {
  final repo = RepositorioProductos([
    Producto(id: '001', nombre: 'Laptop Pro',       categoria: 'Electrónica', precio: 1299.99, stock: 8),
    Producto(id: '002', nombre: 'Ratón Inalámbrico',categoria: 'Periféricos', precio: 34.99,   stock: 0),
    Producto(id: '003', nombre: 'Teclado Mecánico', categoria: 'Periféricos', precio: 89.99,   stock: 15),
    Producto(id: '004', nombre: 'Monitor 4K',       categoria: 'Electrónica', precio: 549.99,  stock: 3),
    Producto(id: '005', nombre: 'Auriculares BT',   categoria: 'Audio',       precio: 149.99,  stock: 12),
    Producto(id: '006', nombre: 'Webcam HD',        categoria: 'Periféricos', precio: 79.99,   stock: 6),
  ]);

  print('📦 Total de productos: ${repo.totalElementos}\n');

  // Capacidad de Filtrable
  print('── Filtrar por categoría "Periféricos" ────');
  repo.filtrarPor('categoria', 'Periféricos').forEach(print);

  print('\n── Filtrar disponibles (stock > 0) ────────');
  repo.filtrarPor('disponible', true).forEach(print);

  // Capacidad de Filtrable (ordenar)
  print('\n── Ordenar por precio (mayor a menor) ────');
  repo.ordenarPor('precio', descendente: true).forEach(print);

  // Capacidad de Paginable
  print('\n── Página 1 (3 por página) ────────────────');
  repo.paginar(pagina: 1, porPagina: 3).forEach(print);

  print('\n── Página 2 (3 por página) ────────────────');
  repo.paginar(pagina: 2, porPagina: 3).forEach(print);

  // Capacidad de Exportable
  print('\n── Exportar CSV ───────────────────────────');
  print(repo.exportarCSV());
}

    RepositorioProductos implementa tres contratos independientes. Cualquier función que espere un Exportable puede recibir este repositorio. Lo mismo con Filtrable y Paginable. Cada parte del sistema puede depender solo del contrato que necesita, sin conocer el resto.

    Interfaces vs Herencia vs Mixins — La guía definitiva¶

    Ya hemos visto los tres mecanismos. Aquí va la comparativa completa para saber cuándo usar cada uno:

    Criterio extends with (mixin) implements
    Relación "es un tipo de" "tiene la capacidad de" "cumple el contrato de"
    Reutiliza implementación ✅ Sí ✅ Sí ❌ No (reimplementas todo)
    Múltiple ❌ Solo una ✅ Varios ✅ Varias
    Obliga a implementar ❌ No ❌ No ✅ Sí
    Crea jerarquía de tipos ✅ Sí ❌ No ✅ Sí
    Uso típico Especializar un tipo Añadir capacidades Definir un contrato

    Árbol de decisión rápido:

    ¿La relación es "X es un tipo de Y"?
├── Sí → extends (herencia)
└── No → ¿Quieres reutilizar implementación sin jerarquía?
          ├── Sí → with (mixin)
          └── No → ¿Solo necesitas garantizar una API?
                    └── Sí → implements (interfaz)

    Combinar extends, with e implements en una sola clase¶

    Dart permite usarlos todos a la vez. El orden es siempre: extends → with → implements:

    abstract class Repositorio {
  String get nombreTabla;
}

mixin Logger {
  void log(String msg) => print('[LOG] $msg');
}

abstract class Exportable {
  String exportarCSV();
}

// ✅ Los tres mecanismos en una sola clase
class ProductoRepositorio extends Repositorio
    with Logger
    implements Exportable {

  @override
  String get nombreTabla => 'productos';

  void guardar(String nombre) {
    log('Guardando "$nombre" en $nombreTabla...');
    // lógica de persistencia
  }

  @override
  String exportarCSV() => 'id,nombre,precio\n001,Laptop,1299.99';
}

void main() {
  final repo = ProductoRepositorio();
  repo.guardar('Laptop Pro');
  print(repo.exportarCSV());
}

    Consejos y buenas prácticas¶

    1. Define interfaces para las dependencias externas de tu app¶

    Siempre que tu código dependa de algo externo (una API, una base de datos, un sistema de almacenamiento), define una interfaz. Así puedes cambiar la implementación sin tocar el código que la usa, y puedes usar implementaciones falsas en los tests.

    // ✅ Tu lógica depende del contrato, no de la implementación concreta
abstract class AlmacenamientoLocal {
  Future<void> guardar(String clave, String valor);
  Future<String?> leer(String clave);
  Future<void> eliminar(String clave);
}

// En producción
class SharedPrefsStorage implements AlmacenamientoLocal { ... }

// En tests
class FakeStorage implements AlmacenamientoLocal { ... }

    2. Mantén las interfaces pequeñas y enfocadas¶

    Una interfaz con 15 métodos es difícil de implementar y de testear. Prefiere varias interfaces pequeñas (Principio de Segregación de Interfaces):

    // ❌ Interfaz demasiado grande
abstract class Repositorio {
  Future<void> guardar(dynamic item);
  Future<dynamic> buscarPorId(int id);
  Future<List> listarTodos();
  String exportarCSV();
  String exportarJSON();
  List filtrarPor(String campo, dynamic valor);
  void sincronizarConServidor();
}

// ✅ Interfaces pequeñas y combinables
abstract class Persistible { Future<void> guardar(dynamic item); }
abstract class Consultable { Future<dynamic> buscarPorId(int id); }
abstract class Exportable  { String exportarCSV(); String exportarJSON(); }

    3. Usa implements cuando necesites garantías en tiempo de compilación¶

    La gran ventaja de las interfaces es que el compilador te obliga a implementar todo el contrato. Si añades un método a la interfaz, todos los errores de implementación aparecen inmediatamente, antes de ejecutar nada.

    4. Nómbralas describiendo la capacidad o el rol¶

    Los mejores nombres de interfaz describen qué hace quien la implementa. Sufijos como -able, -ible o sustantivos de rol funcionan bien:

    // ✅ Nombres descriptivos
abstract class Autenticable { ... }
abstract class Exportable   { ... }
abstract class Notificador  { ... }
abstract class Repositorio  { ... }

    5. implements en tests es tu mejor aliado¶

    Cuando testeas una clase que depende de un servicio externo, puedes crear una implementación falsa en segundos. No necesitas frameworks de mocking si las dependencias están detrás de interfaces:

    // En producción
class ApiCliente implements HttpCliente {
  @override
  Future<String> get(String url) async => /* petición HTTP real */ '';
}

// En test
class FakeHttpCliente implements HttpCliente {
  @override
  Future<String> get(String url) async => '{"ok": true}'; // respuesta fija
}
